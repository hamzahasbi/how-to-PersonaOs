Codeforces (official API), AtCoder (public but undocumented endpoint), and CodeChef and
Kattis (scraped from public profile pages) are all synced. LeetCode remains link-only,
appearing with an honest support label, the handle, and a profile link — never presented
as API-backed data.

## Daily CP dashboard

- The provider selector stays available while a challenge is active; Regenerate may switch providers.
- A failed replacement fetch leaves the current challenge unchanged.

Daily CP challenge snapshots and the public competitive-programming profile stats above
are separate data sets. Daily CP reports today, all-time, and per-provider challenge
outcomes from its authenticated dashboard state.

## Sync behavior

- Syncs are **owner-triggered** from the dashboard (no background jobs) and always run
  through the backend; provider APIs are never called while rendering the public page.
- Per-provider refreshes are rate limited and deduplicated, with bounded submission history.
- Every successful sync stores a normalized snapshot. Identical data refreshes the
  existing snapshot instead of creating duplicate history.
- A failed sync records the error on the connection but **never deletes the last
  successful snapshot** — the public page keeps serving it, flagged as stale after 24h.

### Scraping caveats

CodeChef and Kattis have no supported public stats API, so their adapters scrape the
public profile page HTML. This is inherently more fragile than an API integration:

- Scraped providers depend on page markup that the provider can change without notice.
- When parsing breaks, the sync **fails loudly** (recorded as an error on the connection)
  rather than silently producing wrong data.
- The last successful snapshot keeps serving on the public page (flagged as stale after
  24h) — a broken scrape never overwrites good data with bad data.

## Deduplication and reconciliation

- Solved counts are deduplicated by problem identity (`contestId+index` on Codeforces),
  so multiple accepted submissions count once.
- Providers host disjoint problem sets, so per-provider solved counts are summed for the
  public total without double-counting.
- Imported provider activity is marked `source: "provider"` in snapshots. These remote
  profile snapshots are independent from the authenticated Daily CP challenge history.

## Data ownership and visibility

- Handles are public identifiers, stored backend-side; no provider credentials exist for
  the supported providers, and raw provider responses never reach the browser — only the
  normalized snapshot.
- Each provider connection has a per-provider **public visibility toggle**; unpublished
  or disabled connections never appear on `/competitive`.
- The public endpoint returns a whitelisted payload (handle, profile link, capabilities,
  limitations, last-sync time, stats); internal sync bookkeeping such as error messages
  and visibility flags is never exposed publicly.
- Removing a connection deletes its snapshots (cascade) after an explicit confirmation.
  It does not touch Daily CP challenge history or any other content.

## Public API

`GET /api/public/cp/{handle}/stats` (API-key headers, like other public endpoints)
returns the latest successful snapshot per published provider plus totals and staleness
flags. See the API reference for the schema.

## Contests calendar

The dashboard Contests section at `/dashboard?section=contests` shows a calendar month grid
plus upcoming competitive-programming contests. It displays contests running right now in a
strip at the top, followed by a calendar view and a list of upcoming events.

Contest data comes from [clist.by](https://clist.by), an aggregator that publishes contest
schedules across competitive-programming judges. The judges tracked are determined automatically
from the provider connections already set up in the Competitive section — there is no separate
judge picker. A connected judge that clist cannot cover is listed as "not covered" rather
than silently dropped.

Contest availability depends on the deployment’s configured provider access. If it is
not configured, the dashboard explains that contest data is unavailable.

## Clist aggregated profile

Set your clist.by username under **Dashboard → Profile → Clist profile**. This is the public profile identifier used to build your clist.by link.

Once set, a link to [clist.by](https://clist.by)'s aggregated view of your ratings appears
on the public Competitive page and in the dashboard's Competitive section. Leave it blank
and neither surface renders a link.

The value is your clist.by account name, not a per-judge handle. clist returns a 404 for
unknown coders, so check the link works after saving.

The public Competitive page reads this from the `GET /api/public/cp/:handle/stats` payload
rather than fetching the profile separately, so the link cannot take that page down.
