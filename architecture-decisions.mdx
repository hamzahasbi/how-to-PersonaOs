# Architecture Decisions

PersonaOS uses a shared content model across its public website, private
dashboard, and standalone 3D experience. This overview explains the design
choices; deployment configuration and maintainer runbooks are managed separately.

## One TypeScript workspace

The Next.js website, Express API, and Vite-based 3D application live in a Bun
workspace coordinated by Turborepo. Related changes can evolve together while
each application keeps its own build and runtime responsibilities.

## Markdown as the authored content format

Markdown with validated frontmatter holds articles, project descriptions, and
profile content. Object storage holds the documents; Postgres indexes ownership,
publication state, and versions. This keeps writing portable without requiring
a database column for every content field.

The trade-off is that querying individual fields inside document bodies is less
direct than querying a fully relational content model.

## Backend-owned identity and access

The backend coordinates Supabase authentication, validates requests, and applies
ownership and publication rules. Browser sessions use HTTP-only cookies, while
privileged provider credentials remain server-side.

HTTP-only cookies prevent JavaScript from reading the cookie value directly.
They do not prevent injected scripts from making authenticated requests, so XSS
prevention and authorization checks remain necessary.

## REST and typed dashboard operations

REST and OpenAPI describe the externally documented contracts. tRPC provides
typed calls for dashboard workflows. Both use backend services for validation
and access control; an endpoint being documented does not make it anonymous.

## Managed persistence and versioned schema

Supabase supplies authentication and object storage alongside PostgreSQL.
Drizzle manages typed database access and tracked migrations. Keeping schema
changes in version control makes application and database changes reviewable
together.

## Independent 3D rendering

The cinematic stadium experience is a separate application, keeping its 3D
runtime out of the main website bundle. It loads a snapshot derived from
published profile content and offers a content-only fallback.

Snapshots simplify delivery and reduce runtime dependencies. They must be
regenerated to reflect later edits and should be treated as public artifacts.

## Publication is an explicit boundary

Draft content belongs to the private workspace. Published pages, static exports,
and 3D snapshots are intended for visitors. Authors should review content and
assets before publishing; removing an item later cannot recall copies already
saved by visitors.

Public documentation describes contracts and design choices using synthetic
examples. It does not contain deployment credentials, private account data, or
operator runbooks.
